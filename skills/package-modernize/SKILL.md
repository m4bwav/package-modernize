# package-modernize

Takes one old, published library from "last touched years ago" to a verified new release with current tooling, every issue and pull request answered, the security holes closed and the process documented, without anything reaching a registry until the maintainer approves it. One package, one branch, one release, the same eight phases every time. The phases and the rules in this file hold for every package system; how a phase is done in a given system is in `references/<system>.md` (npm and NuGet complete, the rest unverified). Read this file, then the system's reference, then the plan skeleton; copy templates, never write them from memory.

## Step 0: freshness and the private overlay (every use)

Read `evergreen.json` next to this file. If `verify_at_use` is true, re-check the due `volatile_claims` before relying on them, one search each, then stamp them (`evergreen.py claims <unit> --stamp due`). If `contradiction` is set or today is on or after `next_due`, tell the user in one line, do the task with the current content, then run `evergreen-refresh` in the same session. If `tests.failing` is non-empty, say so in one line and run `evergreen-tune` after the task. Never block the task on a refresh unless the task depends on the stale claim.

Then look for the maintainer's private overlay: the file named by the environment variable `PACKAGE_MODERNIZE_OVERLAY`, else `~/.package-modernize/OVERLAY.md` (open it with the Read tool at its full path, for example `C:\Users\NAME\.package-modernize\OVERLAY.md`; the folder is often a junction or symlink, which file globbing skips). When it exists, read it: it holds the maintainer's identities (registry user, GitHub owner, author line), their standing decisions, machine notes and the inventory of their packages, and it wins over the defaults here. When it does not exist, ask for the identities once in Phase 1 and write them into the plan.

## The shape of a run

- One package, one branch `v<major>`, one release, through the same ritual. A package that needs no rewrite still walks every phase; Phase 1 decides whether a major, a minor or a patch is honest.
- Stops, where the maintainer acts and the run waits: the plan review (Phase 1), the pull request (end of Phase 3), the trusted publisher setup and each staged approval (Phases 5 and 6), and anything the plan did not cover. Silence at the plan review means the recommendations stand; say so when presenting it. A run in a later session takes the rulings and every deletion OK first-hand, in one question to the maintainer, unless the maintainer wrote them into the plan or the kickoff prompt (L-022). Under an agent's automatic permission mode, OKs recorded in files may not carry either: before the post-merge cleanup, list every GitHub write it will make (closures, deletions, ruleset, tag push) in one message and take the go in that session, and put the exact commands in the HANDOFF so the maintainer can run whatever gets refused (L-028).
- Rules that hold everywhere. Nothing reaches a registry from the run's machine: never publish, never create or store a registry token, never approve on the registry's site; workflows stage or wait for an approval, and the maintainer approves each version. No AI attribution in commits, pull requests or files. Ask before deleting anything on GitHub and when a phase's verification fails twice. Research beats recall: re-verify any version number or registry fact older than three months before relying on it, and check every package name on the registry before installing it (hallucinated package names spread through skill files in 2026). Evidence goes to `ai-docs/log.md` as it lands (commit, pull request, workflow run id, registry output); the plan's checkboxes and `ai-docs/HANDOFF.md` are current at every stop. Past about 60 percent of the context window, write the handoff and tell the user to continue in a fresh session.
- Windows: write files with the editor tools, not shell heredocs (they drop backslashes); count byte 13 with `scripts/check-line-endings.mjs` (Git Bash's grep cannot see carriage returns); never `cd` inside a shell call (it moves the session's working directory); use absolute paths and `git -C`; spawn npm and npx through a shell from Node.
- Cloud sessions (Linux, no gh, an egress policy): before Phase 0 plans on a CI runner or Phase 2 on a push, prove push access with `git push --dry-run origin HEAD:refs/heads/probe` (a repository can be attached read-only); collect the GitHub facts `survey-github.sh` needs gh for with the GitHub tools and say so in the survey note; install toolchains from the distribution's archive when the vendor's download hosts are blocked, and record which.

## What every run does the same way

**Survey (Phase 0).** Run `scripts/survey-<system>.sh`; it prints each command above its output, so the file is its own evidence. Then read the clone and the published artifact (it can hold files the repository does not). Record: versions and dates, downloads, dependents by name and how each calls the package, the export shape and how the old README says to call it, runtime dependencies and their distance from current (and whether the package's observable behaviour depends on a dependency's internals), every public method without a direct test, bugs and API oddities (misspellings, odd argument orders, wrong README claims, unbounded loops or allocations on caller input, dead branches, tests asserting the wrong bound), issues and pull requests by author and kind, forks, alerts, every workflow's action pins and their runtimes (a `node20` action stopped running on 2026-09-23, so an old pin fails on day one), webhooks, secrets, security features, dead services (badge, config file, webhook, OAuth app for each), leaked credentials in files and in history. Survey claims can be wrong: check every one against the golden capture, and write the corrections into the kickoff prompt's last section.

**Golden capture (Phase 0).** Before any code change, in a scratch project outside the repository, install the published old version and record every public method's answers to normal, edge and odd inputs (empty strings, numbers where strings go, null and undefined, NaN, negative and out-of-range numbers, huge values, array-likes and Sets, wrapper objects, characters outside the Basic Multilingual Plane). Templates: `scripts/golden-capture-npm.template.cjs` with `templates/npm/test/golden/codec.cjs` (a plain JSON round trip turns NaN and Infinity into null and -0 into 0, the very inputs the capture exists for), `scripts/golden-capture-nuget.template.cs`. A package that calls back, returns Promises or makes requests is captured against a local fixture server started by the capture script, recording each callback's timing, uncaught exceptions and every request the server saw; the internet never enters a recorded case (the system's reference has the recipe). A package with a command line records the published bin's output too: a CLI can be broken while the library works. Commit the JSON, the script as run and the codec. The golden test asserts exact equality and names each deliberate exception in one place; never regenerate the file from the new code, never compare with a tolerance. From the Phase 0 commit on, the golden JSON, the capture script and the codec never change: when the golden test fails, the fix goes in `src/`, or the difference becomes a named exception that the maintainer ruled on in the plan; editing the recording to match the new code is the failure this whole phase exists to prevent (agents reviving repositories edit failing tests; RepoRescue, 2026). A green golden suite counts only after it has been seen red: commit the rewrite, plant one wrong line in `src/` (a changed return, a flipped comparison), build, watch the golden test fail, revert with `git checkout -- <that file>`, watch it pass, and log both runs (before a commit, `git checkout` would restore the old source over the rewrite: L-074 `commit-before-canary`). Fixtures cover only what they record: read ported arithmetic line by line and write oracles from reference implementations for anything algorithmic. Pin the new major's additions in a second golden file captured from the release build.

**Plan (Phase 1).** `references/plan-skeleton.md`. Recommendation first in every row. The questions every plan settles: the compatibility promise and the rule for fixes that would change an old result (a fix goes under a new name; the old name stays exact for one major, marked deprecated); the export shape (plain `require()` must keep working or the break is named); behaviour at the edges, per captured case (keep, fix or refuse, each a changelog line); whether a major is warranted at all and what a patch could do instead; dependencies (zero if platform APIs or a small inlined MIT algorithm can replace them, licence checked); names kept, renamed with aliases, added (one sentence of why each; do not gold-plate); errors (never throw versus typed errors, chosen per package); the runtime floor and matrix (update everything to latest, yet serve the widest audience the package can: the lowest floor and the most targets, platforms and runtimes that cost nothing in safety or upkeep; drop one only for a named reason, never for tidiness; audience means where people are now, so reach them through current tools and trends, not stale or forgotten ones kept alive for a shrinking few); tooling from the system's defaults; the lockfile and the old bot pull requests; dead services; each README badge and image (keep, replace or remove); the release and version; what the package's dependents can rely on next. When two wishes in the kickoff conflict (bounded by the amount versus bit for bit), say so and let the maintainer rule.

**Rewrite (Phase 2).** Golden test first. Tests import the built output, never the source, and run against every build. Every published name keeps working. The library uses no runtime-specific API unless it is a CLI entry. Replace O(n) allocations driven by a caller's number with algorithms bounded by the output. `npm test` and its equivalents never touch the network. README: what it does, install, usage per module system and runtime, API, behaviour at the edges, migration, limits and what the package is not; three live badges (version, CI, downloads), and every other badge and image handled as "Badges and images" below says. CHANGELOG follows Keep a Changelog; a release heading carries its date. Open the pull request with a "For review" list of departures from the plan and unruled questions.

**Badges and images (Phases 0, 1, 2 and the verification).** An old README is full of images that stopped telling the truth. Badges point at shut-down services (David, nodei.co, Gemnasium), at a CI the package left (Travis, AppVeyor), at coverage and vulnerability services the plan drops (Coveralls, codecov, Snyk), or at a chat nobody answers (Gitter). Screenshots, logos and demo GIFs may be hot-linked from dead hosts, show the old API, or use relative paths that break on the registry's page. Phase 0 runs `scripts/check-readme-images.mjs` on the repository README and on the README inside the published package, and lists every image with its finding. A badge from a dead service can still answer 200: the script reads the SVG's text for "not found" or "no longer available". Phase 1 decides each image in the plan's table: keep, replace (with what, and the new URL), or remove (why). Phase 2 applies the decisions. A registry that shows a package icon (NuGet) gets one: when the package has none, Phase 2 draws a basic one with `scripts/make-icon.py` in the maintainer's style (L-070 `generate-missing-icon`). The default badge row is three live badges (registry version, the CI workflow, downloads); add one only when it reports something true and useful, such as a coverage service the plan keeps. Screenshots and diagrams that show old behaviour are re-made from the new version or removed. Images the README keeps use absolute `https://raw.githubusercontent.com/OWNER/REPO/<tag>/...` URLs pinned to a tag, so they render on GitHub and on the registry page. npmjs.com renders the README from the tarball, where relative paths break; nuget.org renders images only from an allow-list of hosts and never from relative paths. Image files stay out of the package through the `files` allowlist or the pack-list test. The verification runs the script on the new README and on the README from the registry after the release, and both must exit 0.

**Independent review (Phase 3).** The prompt in `prompts/review-subagent.md`: read-only, differential fuzzing of old against new, correctness, security, public types, test gaps; at most twelve verified findings. In the second npm run it found twelve real issues that 905 passing tests had missed. Fix or answer every one before asking the maintainer to review.

**Community (Phase 4).** Issues: a comment with the accurate history (cause, the version that fixed it, what the new release does), then close; read old closed issues for behaviour the tests should pin. Old Dependabot or Snyk pull requests on the old lockfile: never merge one by one; after the regenerated lockfile merges and the alert count is 0, close each with one comment naming the merge commit and the removed tool that brought the package in. Human pull requests: read the diff and the discussion; merge what is right with credit in the changelog, otherwise close with the reason and what the new version does instead. Forks: list them; one that only carried a merged pull request needs nothing. Branches with no open pull request (a bot's leftovers, an abandoned fix) get a disposition too; deleting them waits for the maintainer's OK. Expect AI-written pull requests in an old inbox; do not add an unreviewed one.

**Security (Phases 0 to 6).** Leaked tokens: file removed, the maintainer revokes at the provider (history keeps the token; rewriting history achieves nothing once it is revoked), secret scanning and push protection on. Dead-service webhooks removed with the OK; OAuth apps and GitHub Apps uninstalled by the maintainer (the API refuses the `gh` token for that list). Alerts 0 after the lockfile regeneration; the registry's audit tool in CI (signatures verified where the registry offers it; a full audit that fails on dev-only advisories with no fix would block every merge, so scope it). Publishing: 2FA on the registry account, no bypass tokens, trusted publishing bound to one workflow file, a human gate before anything goes live (npm's staged publishing; a GitHub environment with a required reviewer where the registry has no stage; Maven Central's own VALIDATED state), provenance or signatures verified from the registry afterwards, old tokens and CI secrets rotated (the 2025 and 2026 npm worms republished through stolen long-lived tokens). Workflows: `permissions: contents: read` by default, `id-token: write` only in the publish job (which installs nothing, runs no scripts and uses first-party actions only; the GitHub Release is a separate job), tags created only by repository admins (a tag ruleset), a three-day install cooldown for new dependency versions, `persist-credentials: false`, actions pinned to commit SHAs, actionlint and zizmor clean. The library: no network, filesystem, `eval` or prototype-touching merges, no unbounded loops on caller input; a README line saying what the package is not. SECURITY.md with private reporting and supported versions. Never ship a source map or a fixture you did not mean to: a `files` allowlist and a pack-list test.

**Documents (every phase).** In the package repository: AGENTS.md (rules, commands, layout, traps), CLAUDE.md whose first line is `@AGENTS.md`, `.github/copilot-instructions.md` pointing at AGENTS.md, `ai-docs/` (everlast: INDEX, HANDOFF, log, decisions, solutions, plans, notes), README, CHANGELOG, SECURITY.md. Outside it, the maintainer's record: the inventory row, the kickoff prompt with its status line and its corrections section, and this skill's LEARNINGS.md and references. Templates in `templates/<system>/` (read `templates/README.md`); copy and adapt.

**Wrap-up (Phase 7).** HANDOFF.md says what is standing work and when (dates absolute). Every lesson lands in one of three places: a trap or default in `references/<system>.md` with the date, a procedural lesson in LEARNINGS.md with Trigger and Hypothesis, or a correction in the kickoff prompt. Recommend the next package and say what its run can rely on.

## Tools and prior art (checked 2026-09-26)

Delegate to tools rather than reinventing: knip (unused exports and dependencies), npm-check-updates or taze, publint and `@arethetypeswrong/cli --pack`, size-limit, actionlint, zizmor, pinact (SHA pinning), OpenSSF Scorecard for a before and after score, `gh api repos/OWNER/REPO/hooks` for webhooks, `npm deprecate`; for .NET, dotnet-outdated, `dotnet list package --vulnerable --include-transitive`, package validation with `PackageValidationBaselineVersion`, PublicApiAnalyzers. Point at, do not copy: Anthropic's `code-modernization` plugin (1.0.0, 2026-09-25) for a large legacy codebase (its assess, brief and verify vocabulary, byte-for-byte old-versus-new harness, and the canary: a planted one-line break must turn the golden suite red before its green counts), Evil Martians' `secure-npm-package` (the hardened stage-only release job, a `min-release-age` cooldown, an admins-only tag ruleset), Drydock (diff a staged npm version against the published one before the approval), `github/awesome-copilot` `doc-and-modernize` (feasibility spike, safety ladder), `Paldom/node-skills` (npm packaging and release specifics), `dotnet/skills` `nuget-trusted-publishing` and `paulirish/dotfiles` `npm-trusted-publishing` (OIDC setup and its error table), `trailofbits/skills` `open-sourcing` (the pre-public secrets audit), `lirantal/npm-security-best-practices` (the returning-maintainer checklist). Every found skill covers at most three of these phases and none covers the gated release or the registry-side verification; consumer-side upgrade skills and MCP servers help rank dependency targets in Phase 0 only. Agents reviving repositories edit failing tests (RepoRescue, 2026): the golden files and the capture never change after Phase 0 (the Phase 2 canary and untouched check; `scripts/preflight-tag-npm.sh` repeats the check before every tag). RESEARCH.md keeps the list with dates.

## Output

At each stop, one message: the phase reached, the evidence (ids and paths), the decisions or approvals the maintainer must give, and the next single action. At the end of a run: the release verified (or the stop reached cleanly), HANDOFF.md, the inventory row, the corrections to the kickoff prompt, the lessons filed, and the recommended next package.

## While working: capture learnings

If the user corrects you, the same error happens twice, a workaround is found, an environment fact is discovered, or a phase's evidence turns out weaker than this file claims, write it to `LEARNINGS.md` now, and wherever an ID is cited (replies, commits, handoffs, changelog) add a two-to-four-word code name after it, for example L-058 `tool-unescapes-backslash-u`; the number stays the key (format in the protocol; check existing entries first: add, update, retire, or nothing). A trap or a changed default also goes into the system's reference with the date. If a learning proves a claim above wrong, fix it here, log it in `CHANGELOG.md`, and set `contradiction` in `evergreen.json`.

## Maintenance

This skill is evergreen (topic: registry publishing mechanics for npm, NuGet, PyPI, crates.io, Maven Central and Go, library packaging defaults, and how agents modernize legacy libraries safely; tier `fast`, interval set by `evergreen.json`, first due 2026-10-09). Files: `evergreen.json` (state), [RESEARCH.md](RESEARCH.md) (findings and the four-track search plan), [CHANGELOG.md](CHANGELOG.md) (every change, with reasons), [LEARNINGS.md](LEARNINGS.md) (lessons, seeded from the first three runs), [TESTS.md](TESTS.md) and `evals/evals.json` (the cases that prove it and the runs; `evals/run-headless.mjs` runs them through the Claude Code CLI). Protocol: the installed evergreen plugin ([MAINTENANCE.md](MAINTENANCE.md) says how to find it). Refresh with `evergreen-refresh`; test with `evergreen-test`; fix a failure with `evergreen-tune`; audit with `evergreen-audit`. Each run of the skill is also a test of it: what it got wrong goes to LEARNINGS.md and the reference the same day.
