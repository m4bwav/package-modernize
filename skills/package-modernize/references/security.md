# Security (Phases 0 to 6)

Leaked tokens: file removed, the maintainer revokes at the provider (history keeps the token; rewriting history achieves nothing once it is revoked), secret scanning and push protection on. Dead-service webhooks removed with the OK; OAuth apps and GitHub Apps uninstalled by the maintainer (the API refuses the `gh` token for that list). Alerts 0 after the lockfile regeneration; the registry's audit tool in CI (signatures verified where the registry offers it; a full audit that fails on dev-only advisories with no fix would block every merge, so scope it). Publishing: 2FA on the registry account, no bypass tokens, trusted publishing bound to one workflow file, a human gate before anything goes live (npm's staged publishing; a GitHub environment with a required reviewer where the registry has no stage; Maven Central's own VALIDATED state), provenance or signatures verified from the registry afterwards, old tokens and CI secrets rotated (the 2025 and 2026 npm worms republished through stolen long-lived tokens). Workflows: `permissions: contents: read` by default, `id-token: write` only in the publish job (which installs nothing, runs no scripts and uses first-party actions only; the GitHub Release is a separate job), tags created only by repository admins (a tag ruleset), a three-day install cooldown for new dependency versions, `persist-credentials: false`, actions pinned to commit SHAs, actionlint and zizmor clean. The library: no network, filesystem, `eval` or prototype-touching merges, no unbounded loops on caller input; a README line saying what the package is not. SECURITY.md from the template (issues, pull requests or Discussions, with private reporting listed as another option and no advice on what to keep out of public view; supported versions). Never ship a source map or a fixture you did not mean to: a `files` allowlist and a pack-list test.
