# Badges and images

An old README is full of images that stopped telling the truth. Badges point at shut-down services (David, nodei.co, Gemnasium), at a CI the package left (Travis, AppVeyor), at coverage and vulnerability services the plan drops (Coveralls, codecov, Snyk), or at a chat nobody answers (Gitter). Screenshots, logos and demo GIFs may be hot-linked from dead hosts, show the old API, or use relative paths that break on the registry's page. Phase 0 runs `scripts/check-readme-images.mjs` (with `--registry nuget` for NuGet; it defaults to npm, L-106) on the repository README and on the README inside the published package, and lists every image with its finding. A badge from a dead service can still answer 200: the script reads the SVG's text for "not found" or "no longer available". Phase 1 decides each image in the plan's table: keep, replace (with what, and the new URL), or remove (why). Phase 2 applies the decisions. A registry that shows a package icon (NuGet) gets one: when the package has none, Phase 2 draws a basic one with `scripts/make-icon.py` in the maintainer's style (L-070 `generate-missing-icon`). The default badge row is three live badges (registry version, the CI workflow, downloads); add one only when it reports something true and useful, such as a coverage service the plan keeps. Screenshots and diagrams that show old behaviour are re-made from the new version or removed. Images the README keeps use absolute `https://raw.githubusercontent.com/OWNER/REPO/<tag>/...` URLs pinned to a tag, so they render on GitHub and on the registry page. npmjs.com renders the README from the tarball, where relative paths break; nuget.org renders images only from an allow-list of hosts and never from relative paths. Image files stay out of the package through the `files` allowlist or the pack-list test. The verification runs the script on the new README and on the README from the registry after the release, and both must exit 0.
