# Badges and images

An old README is full of images that stopped telling the truth. Badges point at shut-down services (David, nodei.co, Gemnasium), at a CI the package left (Travis, AppVeyor), at coverage and vulnerability services the plan drops (Coveralls, codecov, Snyk), or at a chat nobody answers (Gitter). Screenshots, logos and demo GIFs may be hot-linked from dead hosts, show the old API, or use relative paths that break on the registry's page. Phase 0 runs `scripts/check-readme-images.mjs` (with `--registry nuget` for NuGet; it defaults to npm, L-106) on the repository README and on the README inside the published package, and lists every image with its finding. A badge from a dead service can still answer 200: the script reads the SVG's text for "not found" or "no longer available". Phase 1 decides each image in the plan's table: keep, replace (with what, and the new URL), or remove (why). Phase 2 applies the decisions. Every package gets an icon, whatever its registry shows (see "The icon" below). The default badge row is three live badges (registry version, the CI workflow, downloads); add one only when it reports something true and useful, such as a coverage service the plan keeps. Screenshots and diagrams that show old behaviour are re-made from the new version or removed. Images the README keeps use absolute `https://raw.githubusercontent.com/OWNER/REPO/<tag>/...` URLs pinned to a tag, so they render on GitHub and on the registry page. npmjs.com renders the README from the tarball, where relative paths break; nuget.org renders images only from an allow-list of hosts and never from relative paths. Image files stay out of the package through the `files` allowlist or the pack-list test. The verification runs the script on the new README and on the README from the registry after the release, and both must exit 0.

## The banner

A README opens with a banner image directly under its title, unless the maintainer's overlay says otherwise. Phase 0 notes whether one exists; the plan's badges-and-images table decides it like any other image; Phase 2 makes it when it is missing. It is a scene that says what the package does, wide (1536 by 640 is the tested size), with descriptive alt text, no text in the image, and no real brand's logo or trade dress. Generate it with whatever image tool the maintainer has (the comfyui-gen skill's banner recipe: four seeds, pick from a contact sheet), save it as `.github/images/banner.jpg` with the workflow, prompt and seed beside it, keep it out of the package like every other image, and link it by an absolute raw URL as above. With no image tool available, say so in the plan and leave the row owed; never substitute stock art (L-168 `readme-banner`).

## The icon

Every package leaves the run with an icon, whether or not its registry displays one, because catalogs, listings, marketplaces, the wiki and any other page that shows a picture of the package need one (L-169 `icon-for-every-package`; the maintainer's overlay can opt out). Phase 0 notes whether one exists (in the repository, packed in the package, or on the registry); the plan's badges-and-images table decides it; Phase 2 makes it when it is missing.

- The master is `.github/images/icon.png`, a square 512 by 512 PNG with a transparent outside: one picture or a glyph of one or two characters for what the package does, readable at 32 pixels, no words, no real brand's logo or trade dress. Draw it with `scripts/make-icon.py --size 512` in the maintainer's style (their overlay names the colour and the glyphs of their other packages), or with the maintainer's image tools when the overlay lists them and they ask for richer art (save the workflow, prompt and seed beside it, as for the banner). Open the PNG and look at it before committing.
- Each place that takes an icon gets a copy made from the master, at the size that place asks for: NuGet packs `icon.png` at 128 by 128 at the package root (`make-icon.py` without `--size`, or the master scaled down; see nuget.md), a manifest that names an icon (an editor extension, a marketplace entry) points at the master or a copy, and a catalog submission uploads it. Check the size rule of each catalog when submitting, and write it with the date checked into the system's reference.
- A Claude Code plugin keeps its icon at `.claude-plugin/icon.png` (a square PNG; 1024 by 1024 works) and names it in `.claude-plugin/plugin.json` as `"icon": "./.claude-plugin/icon.png"`: Anthropic's directory reads the listing icon from that field, and without it the portal shows a letter placeholder. The file must be a complete PNG, JPEG, GIF, WebP or SVG inside the plugin folder. Claude Code ignores the field, and `claude plugin validate` accepts it from 2.1.281 (code.claude.com/docs/en/plugins-reference "Directory listing fields" and claude.com/docs/plugins/pre-submission-checklist, both checked 2026-10-11; neither states a pixel size) (L-170 `plugin-json-icon-field`).
- Registries that show no icon (npm, PyPI, crates.io, Maven Central, Go) still get the master in the repository; it stays out of the package like every other image.
- Keep the icon and the banner from contradicting each other: same colour family, same idea. A package that already has an icon keeps it unless the plan says why not; scale it up for the master rather than redrawing it.
